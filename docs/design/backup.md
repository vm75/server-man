# Portable backup planning and preparation

Backup/restore implementation is in progress. Delivered operations cover metadata inventory (`managed_backup_inventory`) and manual bundle preparation (`managed_backup_prepare`), accessible via the shared registry, MCP and Configuration UI. Initial capture produces stage `captured` bundles with checksummed manifests, retaining filesystem metadata but still requiring complete restoration validation. These are not prepared/restorable backups. See the [implementation plan](../plans/declarative-management.md#10-portable-backup-preparation-and-restore) for the full acceptance gates and restore progress.

The inventory pins the authoritative current configuration revision and rechecks it before returning. It includes all declared storage, even unused storage, private-file references, initial image assets and required backend guest-state entries. Each input identifies its logical resources, strategy, bundle path, sensitivity and inspection state. File size/allocation figures are top-level filesystem metadata; they are neither recursive totals nor a backup-size estimate. Current YAML maps to `server-man.yaml` in the eventual bundle.

| Strategy | Current meaning |
| --- | --- |
| `bundle_copy` | Declared owned input whose metadata can be inspected; contents still need collection/checksums |
| `external_data` | Required external storage, excluded pending explicit inclusion and destination-binding review |
| `native_export` | Required instance/custom-volume export target; discovered native identity is recorded when available |
| `native_file` | Native guest-state path discovered from owned metadata; filesystem access and consistent capture remain unverified |

Shared directories and exact duplicate references retain their consumers while `includedBy` identifies an input covering the same data. Future copy code must honor that coverage to avoid duplicate data/private files. Missing/inaccessible/wrong-type inputs, unsafe links, configuration/derived-state collisions and unresolved native/external coverage produce structured issues. Owned bundle-input metadata lookup uses a root-confined directory handle; FIFOs/devices are rejected without opening them. Native paths come from ownership-checked backend metadata and are reported without reading/copying those state paths. Referenced secret files are never read, and raw native configuration is never returned or logged.

Collection/restore requirements explicitly include directory-tree scans, expected mounts, disk backing/dependent files, sparse allocation and filesystem metadata (UID/GID, ACLs, xattrs, SELinux and links). All bundles will need private destinations because configuration/data can contain credentials. Workload consistency and published-share client writes require deliberate quiescence; unpublishing does not disconnect existing Samba sessions. Runtime image availability, host accounts/credentials, bindings and native setup remain explicit destination requirements.

Native VM discovery uses the backend adapters' shared ownership/context checks. Libvirt reads persistent and, while active, live XML, enumerating additional backing/data files, NVRAM and explicitly located TPM state. It reports unsupported block/network/passthrough state and undeclared disks rather than silently omitting data. Libvirt-managed TPM locations are not guessed. Firmware and encryption credentials remain explicit native requirements. Discovery does not prove that XML contains every on-disk dependency. Initial capture now checks standalone physical images while stopped and refuses managed-save/snapshot/checkpoint state; broader native state collection remains required.

Incus first verifies a local non-clustered daemon, then reads owned instance/expanded devices and custom-volume metadata. It resolves `features.storage.volumes` to the effective storage project, exports the complete custom-volume dependency for sub-path attachments, and identifies managed/unmanaged users. Repeated custom volumes share coverage while retaining every managed consumer. Host-mounted disks, native profiles/passthrough devices, missing usage confirmation and unmanaged writers remain explicit issues. Cluster scope is unsupported. Initial stopped instance/custom-volume collection now validates required client flags and streams portable native outputs as described below. Native/live restore acceptance and complete historical snapshot dependency discovery remain open; internal daemon storage is never copied.

Native probes have two seconds per guest and eight seconds total within the shared read deadline; failures/budget exhaustion remain unknown. Device/path/chain/user limits and capped issue details prevent unbounded native enumeration. Runtime state is observed inventory metadata and must be rechecked during preparation; it is not authority to resume a workload later.

Generated native definitions, apply/backup recovery journals, caches and configuration history are excluded from this initial inventory; regenerate definitions from the selected manifest. Host bootstrap/authentication, packages/system services, account/credential setup and native network/pool setup are not portable workload data. Container writable layers, unmanaged volumes and local image caches are excluded; only declared persistent storage is included.

Inventory is bounded to 2,048 combined inputs/requirements and at most 1 MiB of serialized output, under the shared read deadline. It checks cancellation and rejects revision conflicts. Metadata inspection does not prove consistent contents, complete recursive dependencies or a restorable bundle. Privileged metadata completeness, broader libvirt guest-state exports, full native snapshot dependency coverage, interrupted artifact cleanup, restore/conflict handling, metadata/account mapping and pre-start restore validation remain unfinished. Bounded held-root filesystem collection records visible metadata as described below. Initial file capture, checksummed manifest publication and configurable bounded deadlines are implemented as described below.

Native-command fixtures verify ownership, local/project scope, libvirt live/persistent dependencies, TPM uncertainty, shared-volume users/deduplication and timeout behavior, without guest mutations. Temporary-directory tests verify resource coverage, shared-path coverage, no private-content disclosure, missing paths, root escapes, special files, cancellation and bounds. Official SDK tests enforce private-read policy and transport discovery parity; browser fixtures verify honest inventory-stage output and responsive layouts. No real workloads or guest data were backed up or restored.

Native semantics reference the upstream [libvirt domain format](https://libvirt.org/formatdomain.html), [Incus disk devices](https://linuxcontainers.org/incus/docs/main/reference/devices_disk/), [project volume isolation](https://linuxcontainers.org/incus/docs/main/reference/projects/) and [custom-volume export](https://linuxcontainers.org/incus/docs/main/reference/manpages/incus/storage/volume/export/). Those references do not establish installed-version or live-export acceptance.

## Initial backup capture

`managed_backup_prepare` requires write authorization, explicit acknowledgement (`confirm: true`), a reviewed configuration `revision` and an absolute destination directory. The destination must resolve outside the source configuration tree and, if pre-existing, be a private real empty directory. Private sibling staging is pinned beneath a held destination-parent descriptor. Files and nested directory entries are synced before publication; initially absent targets use no-replace rename, while the reviewed private empty directory may be atomically replaced. Parent sync follows the rename. Staging identity, destination state and the user-facing parent identity are rechecked. Failure/cancellation removes only verified owned staging, and never a renamed result. Full source-root and outside-writer exclusion, power-loss acceptance and automated artifact recovery remain open.

Capture runs with a configurable deadline (30–86,400 seconds, default 900), within a trusted 24-hour job bound. The normal job default remains 30 minutes. Only registered tool code can choose the outer job bound; requests cannot override it. Core additionally supports separate binary-stream stdout and diagnostic stderr, avoiding the text-capture limit; the initial Incus exporter uses those sinks directly; libvirt private XML uses the same exclusive private artifact sink.

Unresolved inventory issues, corrupt/incomplete apply journals, unknown runtime states, published shares without client quiescence, external data and unsupported native state/export strategies block capture. Live copies are refused. With quiescence enabled, previously running workloads stop in reverse dependency order and stopped state is verified. Recovery attempts to resume only attempted stops in forward order, with an independent bounded context. A failed dependency prevents its dependants from resuming. Failed actions or unverified active state produce a failed job and identify resources needing recovery. Recovery remains best effort: failed native operations can leave workloads stopped. A private durable record now supports explicit recovery after process restart, as described below.

The manifest records stage `captured`, the config revision, SHA-256 file checksums, filesystem metadata/relationships, capture namespace mappings and workload recovery results. Supported declared files/directories, private files and checksum-pinned initial image assets are copied; payload files use mode 0600 and directories 0700. Source modes/ownership/attributes are retained in the private manifest rather than applied to payloads. Native export records must identify actual private regular files under `native/` with matching sizes/checksums, and every required native object must have a matching verified export. Initial Incus collection implements this object contract. Basic libvirt XML/declared standalone-disk collection now implements the object contract. Broader libvirt state, including NVRAM/TPM/backing chains and native history, remains unsupported; those requirements block capture rather than being omitted. A final configuration revision check precedes publication. Resume failure preserves any published capture and reports failure rather than successful completion.

The UI submits a tracked job and displays completion only after its terminal event. It explicitly calls successful results captured inputs with unverified restore readiness. It never labels job submission as a prepared backup.

Remaining gates include complete capacity/durability and publication hardening, privileged/inode-flag metadata completeness, UID/GID/ACL/SELinux restore review, broader libvirt guest-state collection, full native snapshot dependency discovery, interrupted artifact cleanup and restore validation on disposable hosts. Stage `prepared` must not be used until these requirements are satisfied. No real workloads or guests are mutated by repository verification.

## Interrupted workload recovery

A private owner-only `<configuration-path>.backup.json` records the pinned configuration revision, destination, stage and at most 128 previously running services. An artifact record also captures staging device/inode, parent identity, manifest checksum and publication phase, including when no workloads are running. Each service starts `untouched`; `stop_attempted` is synced before its stop action, then `stopped` after stopped-state verification. An active or unknown observation after an attempted stop becomes `stop_uncertain`: a delayed shutdown may still complete. Only a positively observed stopped state settles that uncertainty before resumption; automatic cleanup and explicit retry leave it pending while still active. Normal cleanup and explicit recovery share the same ordered resume function. Progress becomes `resumed` only after active-state verification; failed services remain `failed` for reviewed retry. Journal files have strict bounded JSON reads and atomic synced replacement shared with apply journals. They contain no secret values or native command output.

The journal survives process restart independently of in-memory jobs. Startup only observes it: the global configuration alert reports pending/corrupt recovery, including when the configuration file is missing. Managed saves/reverts, apply retries, workload lifecycle, provisioning and new captures refuse pending or unreadable recovery. Read-only inspection remains available.

Configuration's **Backup recovery** panel and `managed_backup_recovery_status` expose the current journal, current configuration revision and a review token. `managed_backup_recover` requires acknowledgement, the journal's configuration revision and its current review token. It refuses external config drift, unknown services and unresolved apply journals. Within two minutes it rechecks current revision and native definitions/runtime state, skips already active workloads whose stop had previously settled, and starts only attempted stops after stopped-state verification. Active/unknown observations for an uncertain stop remain pending rather than claiming recovery. Dependants cannot start behind such an uncertain dependency. Unattempted services are never started to satisfy dependencies; absent/inactive dependencies block dependants. Successful progress is recorded after each action; a stale review is refused. This does not replay capture, restore data or modify boot policy.

**Leave workloads as they are** (`managed_backup_release`) requires acknowledgement, the current config revision and review token. It changes no workload, marks the journal `released`, and removes the recovery blocker while preserving recorded failed/pending service states. This permits deliberate manual recovery or configuration repair after external edits, missing configuration or an independently stopped dependency. Release never claims successful resumption or backup completion and does not cancel a native shutdown request that may still finish. Both terminal stages (`complete` and `released`) permit future managed actions.

Abandoned sibling staging and uncertain publication require inspection using the recorded staging/destination/checksum data; recovery never deletes arbitrary destinations or automatically replays exports/copying. Publication pending state survives workload-only recovery, and release acknowledges it without publishing or deleting any files. Native process-crash/disposable-host verification and full bundle restoration remain open. Temporary files and command adapters verify the journal state machine without changing host workloads.

## Initial Incus native collection

The coordinator exports each non-covered inventoried object once rather than asking every VM to export all of its attachments. Each result must match the expected native identity and kind, and its actual private file bytes/size/checksum must verify. Shared custom volumes retain all consumer resource IDs in the manifest. Before quiescing, exporters validate capabilities; a running workload with definition drift is refused because normal resumption could not safely apply that drift. The native dependency inventory is rechecked after stops and after export collection; observed running/transitional guests, new/changed attachments and unresolved checks abort capture.

Incus uses `--force-local`, explicit `local:` object scope and `--project` for every export. Instance archives use `--root-only` so dependent custom volumes are exported separately using their effective storage project. Required `--compression`/instance `--root-only` support is checked against installed CLI help before stops and rechecked at export; missing capabilities produce an actionable failure. No optimized storage format, instance-only or volume-only option is selected: native snapshots are included by default. Filesystem/block volumes produce uncompressed tar output; ISO content retains a separate `.iso` identity. Pool/project/name/content-type identity hashes give private artifact names without cross-project collisions.

Binary stdout streams to an exclusively created held 0600 file under private staging. Native commands receive stdout (`-`) rather than a writable destination path; diagnostics are discarded and errors are sanitized. Streaming checks cancellation and an initial destination free-space budget with a shared 72 MiB private-metadata reserve, hashes exactly written bytes and refuses empty/failed/overwritten artifacts. File identity, type, size and permissions are verified before success. Every managed shared-volume consumer must be verified stopped; unknown/unmanaged users block export. Ownership, scope, attachments and consumer state are checked again after streaming; failed artifacts are removed or their cleanup failure reported.

This is capture-stage collection, not proof of restore readiness or an exclusive lock against outside native writers. Historical snapshot dependencies, archive/import validation, daemon-side transient backup cleanup after cancellation, full filesystem metadata and disposable-host export/import remain acceptance gates. Upstream CLI implementations may use temporary daemon-side backups; local stdout streaming alone does not prove their cleanup. Native removal remains blocked until reviewed retention/restore guarantees are implemented.

Source exports and offline bundle coverage now share a complete streaming uncompressed-tar scan before accepting the artifact. Reads pin real parents and stable private regular files, stop at initial physical size, hash all bytes, and recheck file/parent identity. Scanning bounds visible members to 50,000, path depth to 132, path lengths to 4,096 bytes and retained name/link/PAX metadata to 64 MiB. The real regular `backup/index.yaml` is limited to 1 MiB; its YAML uses the same no-alias/tag/duplicate-key policy as authoritative configuration with depth 64/node 65,536 bounds. Unknown native API fields are retained by the source archive and ignored by the selected-field decoder, rather than copied into a second workload schema.

The scanner rejects traversal/absolute member names, duplicates, non-directory ancestors, unsupported header/optimized/GNU sparse formats, truncation, missing tar end records and nonzero trailing/concatenated data. Direct hardlinks must name a regular member in their own payload section. Declared VM/volume root and snapshot payloads must exist with the expected directory/block-file shape; unrelated sections are refused. The index must match object name, pool, type and non-optimized flags; volume identity and VM name/type/owned ID/UUID must agree with configuration. VM exports require their embedded pool; standalone custom-volume exports may omit that nested block, as the native producer does, while any supplied pool metadata must agree with the index. ISO streams have no index and receive size/privacy/checksum verification only. Absolute guest symlinks and special-file headers may be observed as metadata, but no entry is extracted or activated. Actual native import/link/device/privilege policy must be reviewed before these archives can be called restorable.

Archive validation follows the upstream [index producer](https://github.com/lxc/incus/blob/main/cmd/incusd/backup.go), [backup index](https://github.com/lxc/incus/blob/main/internal/server/backup/backup_info.go), [embedded configuration](https://github.com/lxc/incus/blob/main/internal/server/backup/config/backup_config.go) and [portable payload writer](https://github.com/lxc/incus/blob/main/internal/server/storage/drivers/utils.go). Structured command fixtures retain large binary streams and verify both instance/custom-volume paths. Expanded-device/custom-volume attachment closure, full per-snapshot configuration, advanced native state, ISO format/import semantics, native metadata fidelity and real daemon export/import remain open. The stage remains `captured`.

Snapshot names in the index must now match the embedded storage snapshot records exactly, with no missing/null/duplicate/unknown records and consistent content type and supplied project scope. VM archives additionally require one owned guest snapshot record per name, retaining the configured stable guest ID/UUID. Historical fingerprints/settings may differ from the current desired configuration; record arrays may appear in a different order. Custom-volume exports cannot introduce guest records. The primary volume must also match the expected instance/custom type, name, content and any supplied project. Root-only exports reject embedded dependent-volume records because attached volumes use their own separately inventoried exports. These rules are shared by source export acceptance and offline publication checks.

Name/shape semantics follow the upstream [snapshot API](https://github.com/lxc/incus/blob/main/shared/api/instance_snapshot.go), [storage snapshot API](https://github.com/lxc/incus/blob/main/shared/api/storage_pool_volume_snapshot.go) and [configuration producer](https://github.com/lxc/incus/blob/main/internal/server/storage/backend.go). This establishes record membership/ownership and payload presence, not completeness of historical device dependencies, memory-state compatibility, all snapshot settings or native restore behavior. No snapshot settings are rewritten and no native history is deleted to satisfy validation.

Command semantics were checked against upstream [instance export](https://linuxcontainers.org/incus/docs/main/reference/manpages/incus/export/), [custom-volume export](https://linuxcontainers.org/incus/docs/main/reference/manpages/incus/storage/volume/export/) and the [volume-export CLI source](https://github.com/lxc/incus/blob/main/cmd/incus/storage_volume.go), including stdout handling. Fixture clients verify command scope, snapshot/format flags, exact binary bytes, shared-consumer coverage and failure handling; they do not establish installed-daemon behavior.

## Initial libvirt native collection

The initial supported capture profile uses the existing local BIOS libvirt adapter with owned, explicitly formatted standalone raw/qcow2 file disks. `qemu-img` availability, secure XML access, ownership, disk-definition agreement, accessible real disk paths and native history are validated before quiescence. An initially missing qemu-img is rediscovered on recheck after explicit dependency setup, without mutating shared adapter fields. Capture requires successful read-only managed-save, snapshot and checkpoint queries; existing state or unavailable queries block it. No native history, NVRAM, TPM or backing data is removed to satisfy a check. Broader state capture remains part of the implementation plan.

Libvirt's native `shut off` state is normalized to the shared `stopped` capture state. Queries/actions pin `LC_ALL=C` for stable state parsing. When stopped, each disk is opened through the configuration root with real-path/type/identity checks. The shared image-header gate rejects backing/encryption/external-data/unsupported qcow2 features before `qemu-img` can follow them. Native `info --output=json -f <declared format>` receives a held descriptor path, without forced shared access. Unsupported or hidden backing files, internal snapshots and changing disk metadata fail capture. Those checks run at the stopped boundary before file copying and again around native metadata collection. Creation-only image provisioning shares the standalone-image inspector while retaining its own size limit.

Declared disk bytes are captured through the central file-copy path and checksummed in the bundle. The native artifact is inactive ownership-checked XML requested with `--security-info`, held privately in memory and written to an exclusive 0600 file through the same bounded/cancellable artifact sink as Incus. XML contents and native diagnostics never enter job results or logs. Stopped state, disk metadata and the exact private XML are rechecked afterward; failure removes the artifact. XML assists future native restore, while server-man configuration remains authoritative for managed settings.

Native kernel/initrd/DTB, varstore, sysinfo, QEMU command-line passthrough, launch security, encrypted disks and extra persistent/passthrough devices remain explicit unresolved dependencies. NVRAM/TPM paths and disk chains are inventoried but not silently copied by the initial profile. Managed saves, snapshots/checkpoints, complete native state import/rebinding, full filesystem metadata and disposable-host recovery remain acceptance gates. This profile produces stage `captured`; it does not establish a prepared/restorable backup.

Read-only command semantics were checked against upstream [virsh dumpxml](https://www.libvirt.org/manpages/virsh.html#dumpxml), [managed-save filtering](https://www.libvirt.org/manpages/virsh.html#list), [snapshot inventory](https://www.libvirt.org/manpages/virsh.html#snapshot-list) and [checkpoint inventory](https://www.libvirt.org/manpages/virsh.html#checkpoint-list). Command fixtures verify ownership/scope/history/state transitions without real guest actions. Native `qemu-img` 11.0.3 tests inspect only temporary raw/qcow2 disks; they do not prove live libvirt capture/restore.

Shutdown uncertainty follows the upstream [virsh asynchronous-operation guidance](https://www.libvirt.org/manpages/virsh.html#notes). A still-active observation after a failed stop cannot prove that the request will not complete later. Recovery retains that uncertainty rather than automatically starting dependants or reporting completion.

Source capture and offline bundle verification now share private libvirt XML checks. The private manifest's required `sourceRoot` records the original absolute configuration directory to interpret native disk paths after relocation. It is metadata, not a location to read or restore into: a bundle verifies without access to that host directory. The existing renderer and hardware comparison check name, UUID, owned marker/fingerprints, modeled CPU/memory/architecture/machine, declared disk paths/formats/targets and network identity against authoritative YAML. Existing KiB and versioned-q35 normalization remains supported. Known unsupported boot/security settings, disk encryption/data stores/backing chains and persistent/passthrough devices fail the supported profile checks; a native empty backing-store marker is allowed.

XML is limited to 1 MiB, depth 64 and 65,536 tokens, with cancellation checks. Pre-decoding scanning rejects duplicate attributes and repeated modeled singleton fields, multiple roots, non-whitespace outside the root, directives/DTDs, foreign namespaces outside metadata and unsupported file-source overrides. Metadata/config/XML reads share real held-parent traversal, private type/permission/size checks, bounded content reads, digest checks where pinned and identity/metadata revalidation, including parent retargeting. Parser errors never echo private XML. Source capture uses these checks before quiescence and during export rechecks; offline verification uses them before publication/reconciliation. They do not perform native XSD validation, import XML, activate guests, inspect Incus archive metadata or establish target hardware/metadata compatibility. Advanced native state and full restore remain open. XML remains private evidence; authoritative settings must be regenerated for a reviewed restore.

Identity/namespace and state interpretation follow the upstream [domain XML specification](https://libvirt.org/formatdomain.html); [virsh dumpxml](https://libvirt.org/manpages/virsh.html#dumpxml) distinguishes inactive definitions and security-inclusive data. Temporary fixtures prove offline identity/hardware checks and private error handling; they do not prove native restore behavior.

## Filesystem metadata collection

One filesystem collector serves configuration, owned directories/files, private files and initial image assets. It opens declared parents one component at a time through held roots, verifies the opened inode and never follows leaf symlinks while copying file contents. Directory traversal reads 64 entries per batch, counts every node against one capture-wide 50,000-entry limit, limits depth to 128, and bounds serialized entry metadata to 64 MiB. Duplicate targets, invalid UTF-8 names, special files, escaping/absolute links and changed source entries fail collection. JSON-escapable member names remain intact.

Each declared directory establishes its own Linux mount identity from held descriptor metadata. Descendants must remain on that mount, including bind mounts with the same device number; nested storage needs an explicit separate capture strategy. Metadata/content checks compare inode identity, type, size, mode, UID/GID, link count and modification/change times around copying, with visible attributes rechecked afterward. Access times are recorded before reads; file reads request no-atime access when permitted. This is bounded observation, not a snapshot or lock against outside writers.

The private manifest records file/directory/symlink/hardlink type, numeric ownership, full permission/set-ID/sticky bits, access/modification times, original allocation/link counts, link targets and visible extended attributes. POSIX ACLs and readable SELinux/capability attributes are binary xattr values. Maintained Go Linux FD/no-follow syscall bindings keep attribute reads attached to held objects. Captured hardlinks share one payload inode/checksum and record selected versus original link counts, making aliases outside the selection visible for restore review. Relative symlinks and empty directories have explicit records.

Payload files remain 0600 and directories 0700; source executable/set-ID modes, ACLs and security attributes are not activated in staging. Attribute values appear only in the private manifest, never routine job results/logs. The manifest also records capture UID/GID/groups and bounded `/proc/self/uid_map`/`gid_map` data. Linux can hide privileged attribute namespaces, so coverage is explicitly `visible` or `unsupported_source_fs`; absence is not proof that every privileged label was collected. Complete inode flags, account/mapping review and target policy validation remain open.

File copying hashes logical bytes, retains sparse zero regions, stops at the initially observed size and rejects changed metadata. Initial free-space estimates use allocated size where known. Both file and native artifact sinks reserve 72 MiB for bounded private metadata and reject writes beyond observed free-space budgets; unknown directory capacity and concurrent outside allocation can still cause a failed capture. Manifest encoding is compact and bounded; summary counts are filesystem/native/manifest entries rather than just payload files. Recursive file/directory sync is implemented; power-loss acceptance and restore verification remain required before stage `prepared`.

Confinement and visibility follow the upstream [Go root API scope](https://go.dev/src/os/root.go) and [Linux extended-attribute interfaces](https://man7.org/linux/man-pages/man2/listxattr.2.html). Temporary fixtures verify real ACL/binary-attribute capture, private payload permissions, hardlinks, empty directories, relative links, held-root replacement, mount-ID refusal, global limits and cancellation. They do not prove a portable restore or complete privileged namespace access.

## Capture publication and interrupted artifacts

Capture validates its private manifest before encoding/publication. The shared metadata validator checks the captured-stage/version contract, configuration checksum/revision agreement, entry/depth bounds, unique nonescaping paths, reserved-path separation, ancestor types, timestamps/modes, bounded visible attributes and hardlink metadata/count relationships. Native artifact records must have matching backend identities, paths, sizes and checksums. These are metadata assertions; actual native identity/coverage and payload bytes require separate verification.

An internal manifest reader supports later restore/reconciliation work through a held bundle root. It accepts only a real private bounded `manifest.json` regular file, checks identity/metadata around reading, rejects invalid UTF-8, duplicate JSON keys, excessive nesting, unknown fields and trailing values, then applies the same validator. Errors do not echo private metadata. No restore or public verification operation is exposed by this reader. It does not scan/hash payloads, validate archives, resolve account mappings or establish a complete/restorable bundle.

Capture additionally runs a shared held-root tree verifier before syncing/publication. It pins interpretation to the reviewed manifest checksum and checks that every filesystem/native payload has the recorded type, logical size and SHA-256, with relative symlink targets and real hardlink identities/counts. Hardlinked names share one checksum read, with inode metadata agreement required across aliases. Private directory/file permissions and mount identities are checked, parents are opened one component at a time, and symlink targets are never traversed. Only recorded nodes, required implicit directories and the manifest itself are allowed; unused standard bundle directories are no longer created eagerly. Missing nodes, unlisted data, unexpected aliases outside the bundle, special files and changed entries fail verification. Traversal uses 64-entry batches, the capture depth bound plus four bundle levels, and at most 58,192 entries. A final metadata pass checks observed entries again. All checks are observations rather than locks against outside writers.

File hashing reads exactly the initial logical size with cancellation checks and compares inode/size/ownership/mode/link/change metadata afterward. Growth cannot extend a checksum read indefinitely; growth, truncation or observed replacement fails. Results/errors contain no payload or private metadata contents. This verifies byte/link agreement with a checksummed index, not authenticity, native archive/import validity, completeness of discovered native dependencies, account mapping or power-loss durability. Stage remains `captured`; restore and standalone public bundle verification remain unfinished. Interrupted publication has the reviewed reconciliation operation below.

Offline coverage checks read the real bounded `server-man.yaml` leaf through the held bundle root, compare identity/metadata around reading, require the recorded configuration checksum and use the shared strict YAML parser/schema. Source inventory and coverage derive declared file inputs from one function. All configured storage roots, private files and initial-image assets must have compatible explicit records; assets must match configured checksums, and private-file source modes must be owner-only. Declared directories cover their recorded descendants; filesystem records outside declared roots/references are rejected. Symlink targets must stay inside a declared directory that also covers the link; overlapping declarations retain the outer collection boundary. Unresolved external storage prevents coverage success. This does not probe or alter the current host.

Every configured VM must have exactly one primary export record with its backend-derived name and expected kind. Incus instance records must match explicit project/root-pool bindings and block content; libvirt records cannot introduce foreign scope fields. Duplicate native objects and unknown/wrong consumers or kinds fail coverage. Custom-volume records require supported scoped identities and Incus VM consumers. Running/resumed/failed workload lists must be unique, reference configured services and account for the prior running set without overlap. These checks run before both initial publication and reviewed publication reconciliation. Libvirt XML and Incus archive/index contents receive the checks described above. Incus expanded-device/attached-volume and full snapshot configuration completeness still require validation; a plausible index alone cannot establish those facts. Advanced guest state, target identity/policy mapping and restore remain open.

Publication uses a held parent root/file descriptor and a private random sibling staging name. The collector/native exporters receive a path anchored through that descriptor. Every capture records an artifact journal before stop/data operations, even with an empty workload set. Artifact phases are `building`, `synced`, `publishing`, `published`, `discarded`, `uncertain` and explicit `released`; synced/publishing/published phases require the manifest checksum. Location/nonce/parent/inode fields are validated on private reads.

After writing the bounded private manifest, a bounded traversal syncs regular files and every directory from children to root; symlink targets are never followed. It rejects unexpected special files, changed nodes and nested mounts. The parent is synced to persist staging existence, then checksum and rename intent are durably journaled. Initially absent destinations use `renameat2(RENAME_NOREPLACE)`, so an appearing destination is not replaced. A pre-existing reviewed empty private directory is identity/emptiness checked immediately before atomic directory replacement; Linux rejects replacing a populated directory. There is no exclusive lock against outside administrators modifying a reviewed directory between checks.

Rename is relative to the held parent descriptor. A successful rename is marked in memory before parent sync, so later failures never recursively delete the final result. Destination/parent identity checks and parent fsync precede the `published` journal update. An uncertain rename/sync or recovery-record update reports failure and preserves data for review. Pre-rename cleanup checks staging identity, removes only that owned tree through the held parent, and syncs removal before marking `discarded`; changed staging is left for inspection.

Configuration shows recorded publication phase, staging location and manifest checksum. Publication-only pending records remain visible after workload recovery and offer explicit release rather than workload replay. Release performs no publish/delete operation. A recorded phase/checksum is not a substitute for future restore validation of actual bytes, identities and metadata.

`managed_backup_publish` / **Verify and finish publication** reconciles an interrupted artifact through the shared registry and serialized job lock, with explicit confirmation. The current configuration revision and recovery token must match the review. It opens the recorded parent and checks its device/inode, then accepts exactly one location: the recorded private staging directory with an absent destination, or the same recorded directory already at the destination with staging absent. A different directory, even an empty destination, is a conflict. Missing/replaced/symlinked locations are preserved for inspection. A finalized recorded manifest checksum is required; incomplete captures without one cannot be published through recovery.

Reconciliation shares the full byte/link/tree verifier and additionally requires the manifest's configuration revision to match the capture journal. It syncs the verified tree/parent, rechecks the current review, persists `publishing`, and performs descriptor-relative no-replace rename only if needed. Parent sync, destination/parent identity checks and a fresh review check precede `published`. Verification/publication shares capture's 30–86,400 second deadline (default 900), under a trusted 24-hour job limit. Failure/cancellation after intent retains pending publication and all data; a reviewed retry distinguishes staged versus already renamed data. Neither path starts workloads, changes their recovery states, imports native data, marks the bundle prepared/restorable, deletes staging or replaces a destination. Release remains the explicit alternative; startup never reconciles automatically.

Linux primitives use the maintained `golang.org/x/sys/unix` package rather than local architecture syscall numbers or unsafe attribute bindings. Semantics follow [Linux rename/no-replace behavior](https://man7.org/linux/man-pages/man2/rename.2.html) and [file/directory sync requirements](https://man7.org/linux/man-pages/man2/fsync.2.html). Fixtures cover absent/reviewed-empty publication, namespace/staging replacement, conflicts/data preservation, cancellation/special-file rejection and a failure between rename and parent sync. Actual power-loss, external-writer races and automatic interrupted-artifact completion remain open acceptance gates.
