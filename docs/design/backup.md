# Portable backup planning and preparation

Backup/restore implementation is in progress. Delivered operations cover metadata inventory (`managed_backup_inventory`) and manual bundle preparation (`managed_backup_prepare`), accessible via the shared registry, MCP and Configuration UI. Initial capture produces stage `captured` bundles with checksummed manifests, explicitly lacking complete restoration metadata. These are not prepared/restorable backups. See the [implementation plan](../plans/declarative-management.md#10-portable-backup-preparation-and-restore) for the full acceptance gates and restore progress.

The inventory pins the authoritative current configuration revision and rechecks it before returning. It includes all declared storage, even unused storage, private-file references, initial image assets and required backend guest-state entries. Each input identifies its logical resources, strategy, bundle path, sensitivity and inspection state. File size/allocation figures are top-level filesystem metadata; they are neither recursive totals nor a backup-size estimate. Current YAML maps to `server-man.yaml` in the eventual bundle.

| Strategy | Current meaning |
| --- | --- |
| `bundle_copy` | Declared owned input whose metadata can be inspected; contents still need collection/checksums |
| `external_data` | Required external storage, excluded pending explicit inclusion and destination-binding review |
| `native_export` | Required instance/custom-volume export target; discovered native identity is recorded when available |
| `native_file` | Native guest-state path discovered from owned metadata; filesystem access and consistent capture remain unverified |

Shared directories and exact duplicate references retain their consumers while `includedBy` identifies an input covering the same data. Future copy code must honor that coverage to avoid duplicate data/private files. Missing/inaccessible/wrong-type inputs, unsafe links, configuration/derived-state collisions and unresolved native/external coverage produce structured issues. Owned bundle-input metadata lookup uses a root-confined directory handle; FIFOs/devices are rejected without opening them. Native paths come from ownership-checked backend metadata and are reported without reading/copying those state paths. Referenced secret files are never read, and raw native configuration is never returned or logged.

Collection/restore requirements explicitly include directory-tree scans, expected mounts, disk backing/dependent files, sparse allocation and filesystem metadata (UID/GID, ACLs, xattrs, SELinux and links). All bundles will need private destinations because configuration/data can contain credentials. Workload consistency and published-share client writes require deliberate quiescence; unpublishing does not disconnect existing Samba sessions. Runtime image availability, host accounts/credentials, bindings and native setup remain explicit destination requirements.

Native VM discovery uses the backend adapters' shared ownership/context checks. Libvirt reads persistent and, while active, live XML, enumerating additional backing/data files, NVRAM and explicitly located TPM state. It reports unsupported block/network/passthrough state and undeclared disks rather than silently omitting data. Libvirt-managed TPM locations are not guessed. Firmware and encryption credentials remain explicit native requirements. Discovery does not prove that XML contains every on-disk dependency; stopped-state physical checks and native snapshot/managed-save handling remain required.

Incus first verifies a local non-clustered daemon, then reads owned instance/expanded devices and custom-volume metadata. It resolves `features.storage.volumes` to the effective storage project, exports the complete custom-volume dependency for sub-path attachments, and identifies managed/unmanaged users. Repeated custom volumes share coverage while retaining every managed consumer. Host-mounted disks, native profiles/passthrough devices, missing usage confirmation and unmanaged writers remain explicit issues. Cluster scope is unsupported. Native instance/custom-volume exports still need capability validation and consistent capture; internal daemon storage is never copied.

Native probes have two seconds per guest and eight seconds total within the shared read deadline; failures/budget exhaustion remain unknown. Device/path/chain/user limits and capped issue details prevent unbounded native enumeration. Runtime state is observed inventory metadata and must be rechecked during preparation; it is not authority to resume a workload later.

Generated native definitions, apply/backup recovery journals, caches and configuration history are excluded from this initial inventory; regenerate definitions from the selected manifest. Host bootstrap/authentication, packages/system services, account/credential setup and native network/pool setup are not portable workload data. Container writable layers, unmanaged volumes and local image caches are excluded; only declared persistent storage is included.

Inventory is bounded to 2,048 combined inputs/requirements and at most 1 MiB of serialized output, under the shared read deadline. It checks cancellation and rejects revision conflicts. Metadata inspection does not prove consistent contents, complete recursive dependencies or a restorable bundle. Complete metadata-preserving tree streaming, concrete native exports, interrupted artifact cleanup, restore/conflict handling, metadata/account mapping and pre-start restore validation remain unfinished. Initial file capture, checksummed manifest publication and configurable bounded deadlines are implemented as described below.

Native-command fixtures verify ownership, local/project scope, libvirt live/persistent dependencies, TPM uncertainty, shared-volume users/deduplication and timeout behavior, without guest mutations. Temporary-directory tests verify resource coverage, shared-path coverage, no private-content disclosure, missing paths, root escapes, special files, cancellation and bounds. Official SDK tests enforce private-read policy and transport discovery parity; browser fixtures verify honest inventory-stage output and responsive layouts. No real workloads or guest data were backed up or restored.

Native semantics reference the upstream [libvirt domain format](https://libvirt.org/formatdomain.html), [Incus disk devices](https://linuxcontainers.org/incus/docs/main/reference/devices_disk/), [project volume isolation](https://linuxcontainers.org/incus/docs/main/reference/projects/) and [custom-volume export](https://linuxcontainers.org/incus/docs/main/reference/manpages/incus/storage/volume/export/). Those references do not establish installed-version or live-export acceptance.

## Initial backup capture

`managed_backup_prepare` requires write authorization, explicit acknowledgement (`confirm: true`), a reviewed configuration `revision` and an absolute destination directory. The destination must resolve outside the source configuration tree and, if pre-existing, be a private real empty directory. Private sibling staging is published with one Linux directory rename; a nonempty destination prevents publication. File and metadata writes are synced; complete directory-tree durability and held-handle destination/source race hardening remain open. Failure/cancellation attempts to remove staging.

Capture runs with a configurable deadline (30–86,400 seconds, default 900), within a trusted 24-hour job bound. The normal job default remains 30 minutes. Only registered tool code can choose the outer job bound; requests cannot override it. Core additionally supports separate binary-stream stdout and diagnostic stderr, avoiding the text-capture limit; concrete native exporters remain unfinished.

Unresolved inventory issues, corrupt/incomplete apply journals, unknown runtime states, published shares without client quiescence, external data and unsupported native state/export strategies block capture. Live copies are refused. With quiescence enabled, previously running workloads stop in reverse dependency order and stopped state is verified. Recovery attempts to resume only attempted stops in forward order, with an independent bounded context. A failed dependency prevents its dependants from resuming. Failed actions or unverified active state produce a failed job and identify resources needing recovery. Recovery remains best effort: failed native operations can leave workloads stopped. A private durable record now supports explicit recovery after process restart, as described below.

The manifest records stage `captured`, the config revision, SHA-256 file checksums, file modes/times and workload recovery results. Supported declared files/directories, private files and checksum-pinned initial image assets are copied; private files use mode 0600. Native export records must identify actual private regular files under `native/` with matching sizes/checksums, and every required native object must have a matching verified export. Current backend adapters do not implement complete native exports, so affected captures are blocked. A final configuration revision check precedes publication. Resume failure preserves any published capture and reports failure rather than successful completion.

The UI submits a tracked job and displays completion only after its terminal event. It explicitly calls successful results captured inputs with unverified restore readiness. It never labels job submission as a prepared backup.

Remaining gates include recursive scan/capacity bounds, source/destination race hardening, ownership/ACL/xattr/SELinux/directory/link metadata, native guest/volume exports, interrupted artifact cleanup, complete directory durability and restore validation on disposable hosts. Stage `prepared` must not be used until these requirements are satisfied. No real workloads or guests are mutated by repository verification.

## Interrupted workload recovery

A private owner-only `manifestPath.backup.json` records the pinned configuration revision, destination, stage and at most 128 previously running services. Each service starts `untouched`; `stop_attempted` is synced before its stop action, then `stopped` after stopped-state verification. Normal cleanup and explicit recovery share the same ordered resume function. Progress becomes `resumed` only after active-state verification; failed services remain `failed` for reviewed retry. Journal files have strict bounded JSON reads and atomic synced replacement shared with apply journals. They contain no secret values or native command output.

The journal survives process restart independently of in-memory jobs. Startup only observes it: the global configuration alert reports pending/corrupt recovery, including when the configuration file is missing. Managed saves/reverts, apply retries, workload lifecycle, provisioning and new captures refuse pending or unreadable recovery. Read-only inspection remains available.

Configuration's **Backup recovery** panel and `managed_backup_recovery_status` expose the current journal, current configuration revision and a review token. `managed_backup_recover` requires acknowledgement, the journal's configuration revision and its current review token. It refuses external config drift, unknown services and unresolved apply journals. Within two minutes it rechecks current revision and native definitions/runtime state, skips already active workloads, and starts only attempted stops. Unattempted services are never started to satisfy dependencies; absent/inactive dependencies block dependants. Successful progress is recorded after each action; a stale review is refused. This does not replay capture, restore data or modify boot policy.

**Leave workloads as they are** (`managed_backup_release`) requires acknowledgement, the current config revision and review token. It changes no workload, marks the journal `released`, and removes the recovery blocker while preserving recorded failed/pending service states. This permits deliberate manual recovery or configuration repair after external edits, missing configuration or an independently stopped dependency. Release never claims successful resumption or backup completion. Both terminal stages (`complete` and `released`) permit future managed actions.

Abandoned sibling staging and uncertain publication still require inspection; recovery never deletes arbitrary destinations or automatically replays exports/copying. Native process-crash/disposable-host verification and full bundle restoration remain open. Temporary files and command adapters verify the journal state machine without changing host workloads.
