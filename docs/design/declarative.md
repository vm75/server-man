# Declarative configuration foundation

The declarative implementation is in progress. Its [implementation plan](../plans/declarative-management.md) tracks the complete target; the functionality below describes the current foundation only.

`internal/declarative` owns the typed workload YAML independently of transports. The initial schema includes service, storage, binding, private-file reference and share definitions. Container definitions default to Podman with Quadlet; Docker accepts Compose only. VM backend choices are libvirt and Incus. Parsing rejects unknown/duplicate fields, aliases, anchors, explicit tags, multiple documents and files above 1 MiB. Domain validation checks references, dependency cycles, enabled dependencies, native field constraints and duplicate guest identities. The schema still needs additional target features before backend implementation is complete.

The private configuration store resolves relative asset paths against the manifest location. Saves validate before publication, generate persistent VM UUID/MAC values when absent, preserve existing identities and reject identity changes. An owner-only temporary file is synced and renamed, followed by directory sync. Callers must hold the shared management lock around the operation; external edits are checked by revision immediately before publication, but this is not a filesystem transaction with arbitrary external editors. A failed final directory sync can follow successful replacement and must be treated as uncertain publication by the future coordinator.

Up to eight previous configurations are retained in an adjacent owner-only `.history` directory, addressed by hashes of their exact original bytes. Invalid YAML can be read through the same private-file policy and repaired with its current revision; the invalid original is retained in history. UI saves normalize YAML formatting. Private reference files are never opened to collect configuration history.

The bootstrap `manifestPath` setting accepts an absolute path. When omitted, it selects `server-man.yaml` inside `stateDir`. Startup does not create that file or any workload data. Shared registry tools provide:

- `managed_config_read`: private configuration editor content and revision, gated by `allowWrites`, including malformed YAML for recovery.
- `managed_config_validate`: typed validation and file preflight of a candidate without saving it.
- `managed_config_health`: validity and file preflight of the current configuration, with missing/invalid configurations remaining inspectable.

File preflight reports missing/wrong-type paths, symlink escapes and private-file permission problems, and propagates blockers to referencing services/shares. It never creates missing directories or disks. Expected mount sources are compared with the visible filesystem covering the data path using bounded Linux mount inventory. The `storage.mount` value is an absolute mount source (for example `/dev/mapper/data`); unsupported identities remain blocked. DAC read/traversal and required write access are checked without creating data. Legacy static inspection responses retain `runtimeChecked: false`; the newer readiness operations below add native probes without claiming image/guest/application health.

The coordinator now also registers `managed_config_plan`, `managed_config_save`, `managed_apply_status`, and `managed_apply_retry`. Saves run as acknowledged, serialized management jobs. The coordinator journals intent to an adjacent private `.apply.json` file before persisting desired YAML, then records per-resource publication/verification outcomes. A missing adapter or failed apply leaves desired configuration saved and the job failed/blocked. A first Podman Quadlet adapter is wired into this coordinator; other selected backends remain unavailable until implemented.

Resource fingerprints include storage/private-file/network references. Changes apply in dependency order, removals in reverse order; unchanged resources are inspected before being treated as no-ops. Native errors are sanitized. Retry checks desired revision and native observed state, reuses matching definitions and refuses uncertain destructive removal replay. An interrupted prepared operation whose configuration was never saved can be marked aborted. Incomplete transitions block subsequent saves until inspected/retried. The journal is progress metadata, never an independent definition store. Remaining backend adapters, complete live/deferred revision tracking, full fault injection/recovery and privileged publication remain open work, along with complete preflight, UI and portable backup. Existing host modules continue operating independently until their planned replacements are implemented and verified.

## Initial Quadlet adapter

`Quadlet` renders private owned `.container` and `.network` sources below the application account's user Quadlet search directory (`$XDG_CONFIG_HOME/containers/systemd/server-man/<service>`). Names are deterministic. Containers share an application network with container-ID DNS aliases; applications are not implicitly pods. Fixed generator dry-runs validate isolated candidates and require every expected service in output. This does not launch containers or reload host services.

Publication rejects foreign/manual changes and final symlinks, atomically replaces owned files and removes only known prior outputs. A user-manager reload registers definitions. New applications remain stopped. Immediate edits restart only previously running members when runtime settings changed. Enable/disable changes source `[Install]` boot dependencies without restarting members or invoking `systemctl enable` on generated services. Source and active-container fingerprints distinguish registered settings from running settings; deferred changes can report `restart_required`.

`managed_service_start`, `stop`, `restart`, `enable` and `disable` are shared job operations. Start/restart check required file references, registered definitions/dependencies and cgroup v2; stop verifies the resulting unit states. Enable/disable persist authoritative boot policy through the coordinator. User-manager/Podman/generator access remains required; startup configuration alone does not establish lingering or successful boot behavior.

Current limits: no full health/readiness schema or checks, complete runtime prerequisite inventory, partial-group status UI, comprehensive native restart/failure tests or verified boot integration. Dependencies currently require other Quadlet applications. Removed definitions require stopped workloads; automatic uncertain removal replay is refused. Network cleanup, drop-in conflict detection, publication crash recovery and restore behavior require further implementation/verification. Native live mutation tests have not run; existing tests use command fixtures and isolated installed-generator dry-runs only.

## Readiness and Applications status

`managed_config_check` refreshes native prerequisites and static filesystem checks; `managed_services` supplies redacted configuration health and selected per-application state. Quadlet prerequisites enumerate missing programs, engine access, cgroup v2, user-manager access and lingering. Native results are cached for ten seconds per configuration, with a separate runtime-check timestamp and explicit refresh. Issues propagate to affected resources and their dependent services. Missing adapters and unavailable checks produce blocked/unknown results rather than a readiness claim. Lingering blocks boot enablement but is separate from current-run startup requirements.

The initial Applications page shows lifecycle controls, running state, boot policy, configuration status and actionable startup issues. It disables start/restart/enable when the corresponding known requirements are blocked. Existing host service/software screens retain direct management. Guided definition/edit forms, malformed-config editor UI, backend-specific details, complete runtime probes, account mapping/SELinux checks, image availability and restore workflows remain open implementation work.
