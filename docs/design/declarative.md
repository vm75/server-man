# Declarative configuration foundation

The declarative implementation is in progress. Its [implementation plan](../plans/declarative-management.md) tracks the complete target; the functionality below describes the current foundation only.

`internal/declarative` owns the typed workload YAML independently of transports. The initial schema includes service, storage, binding, private-file reference and share definitions. Container definitions default to Podman with Quadlet; Docker accepts Compose only. VM backend choices are libvirt and Incus. Parsing rejects unknown/duplicate fields, aliases, anchors, explicit tags, multiple documents and files above 1 MiB. Syntax and typed-field errors report available numeric YAML line locations without returning parser text or scalar values. Shared YAML structural validation additionally bounds configuration depth to 128 and nodes to 1,048,576; private native backup indexes use tighter limits. Domain validation checks references, dependency cycles, enabled dependencies, native field constraints and duplicate guest identities. The schema still needs additional target features before backend implementation is complete.

The private configuration store resolves relative asset paths against the manifest location. Saves validate before publication, generate persistent VM UUID/MAC values when absent, preserve existing identities and reject identity changes. An owner-only temporary file is synced and renamed, followed by directory sync. Callers must hold the shared management lock around the operation; external edits are checked by revision immediately before publication, but this is not a filesystem transaction with arbitrary external editors. A failed final directory sync can follow successful replacement and must be treated as uncertain publication by the future coordinator.

Up to eight previous configurations are retained in an adjacent owner-only `.history` directory, addressed by hashes of their exact original bytes. Invalid YAML can be read through the same private-file policy and repaired with its current revision; the invalid original is retained in history. UI saves normalize YAML formatting. Private reference files are never opened to collect configuration history.

One private YAML document contains an optional `server` section and all managed resource sections. `-config` selects this file; its default is `~/.config/server-man/server-man.yaml` (or under `XDG_CONFIG_HOME`). There is no bootstrap JSON or `manifestPath`. Startup validates server settings; invalid typed resource definitions remain inspectable for repair. Typed edits and lifecycle policy saves preserve server settings. Server-only changes skip native drift repair and require a restart before further managed operations; combined server/native-resource changes are rejected. Startup does not create configuration or workload data. Shared registry tools provide:

- `managed_config_read`: private configuration editor content and revision, gated by `allowWrites`, including malformed YAML for recovery.
- `managed_config_validate`: typed validation and file preflight of a candidate without saving it.
- `managed_config_health`: validity and file preflight of the current configuration, with missing/invalid configurations remaining inspectable.

File preflight reports missing/wrong-type paths, symlink escapes and private-file permission problems, and propagates blockers to referencing services/shares. It never creates missing directories or disks. Expected mount sources are compared with the visible filesystem covering the data path using bounded Linux mount inventory. The `storage.mount` value is an absolute mount source (for example `/dev/mapper/data`); unsupported identities remain blocked. DAC read/traversal and required write access are checked without creating data. Legacy static inspection responses retain `runtimeChecked: false`; the newer readiness operations below add native probes without claiming image/guest/application health.

The coordinator now also registers `managed_config_plan`, `managed_config_save`, `managed_apply_status`, and `managed_apply_retry`. Saves run as acknowledged, serialized management jobs. The coordinator journals intent to an adjacent private `.apply.json` file before persisting desired YAML, then records per-resource publication/verification outcomes. A missing adapter or failed apply leaves desired configuration saved and the job failed/blocked. Initial Podman Quadlet, Podman Compose and Docker Compose adapters are wired into the coordinator; an initial existing-disk libvirt adapter is also connected. An initial local Incus VM adapter is also connected; authoritative Samba/NFS adapters are now also connected.

An owned-artifact byte conflict has a specific, controlled public repair message in both the failed job and durable resource result. Arbitrary native errors remain generic to prevent diagnostic/configuration leakage. Configuration renders durable per-resource apply states and messages, including partial success, after refresh/navigation; viewing a failure never retries it. Explicit retry remains separate from artifact repair. A reviewed artifact repair workflow and a persisted publication manifest remain open; this diagnostic does not weaken file ownership checks or add compatibility/import behavior.

Resource fingerprints include storage/private-file/network references. Changes apply in dependency order, removals in reverse order; unchanged resources are inspected before being treated as no-ops. Native errors are sanitized. Retry checks desired revision and native observed state, reuses matching definitions and refuses uncertain destructive removal replay. An interrupted prepared operation whose configuration was never saved can be marked aborted. Incomplete transitions block subsequent saves until inspected/retried. The journal is progress metadata, never an independent definition store. Remaining backend adapters, complete live/deferred revision tracking, full fault injection/recovery and privileged publication remain open work, along with complete preflight, UI and portable backup. Host system services, packages, share setup and read-only native share inspection remain independent; legacy container/machine and direct native share-edit tools have been removed.

## Initial Quadlet adapter

Unit serialization distinguishes raw scalar directives from tokenized words. Quadlet Image, Volume and EnvironmentFile values and Compose WorkingDirectory paths use literal scalar encoding; Environment and Exec retain word quoting. All forms escape systemd percent specifiers, and ambiguous controls/backslashes or outer whitespace are refused before publication. Isolated native generator tests check the resulting command line for unwanted literal argument quotes.

`Quadlet` renders private owned `.container` and `.network` sources below the application account's user Quadlet search directory (`$XDG_CONFIG_HOME/containers/systemd/server-man/<service>`). Names are deterministic. Containers share an application network with container-ID DNS aliases; applications are not implicitly pods. Fixed generator dry-runs validate isolated candidates and require every expected service in output. This does not launch containers or reload host services.

Typed memory limits are forwarded as fixed `PodmanArgs=--memory=<MiB>m` values. This keeps the container limit intact without depending on the newer Quadlet `Memory=` directive, which the current Debian stable generator rejects. There is one rendering path, no version switch or provider downgrade. Native dry-runs check that the resulting Podman command contains the requested limit.

Both Podman adapters share a managed-network prerequisite for the executable `nft`, supplied by the shared native `nftables` dependency preset. Podman info can succeed when this tool is absent even though Netavark then fails during container startup. Readiness checks discovery in the workload account's PATH and blocks current/boot activation if missing or non-executable. This is a baseline dependency even with an alternative native firewall driver; it does not select a driver, query/change rules or enable the nftables host service. Docker retains its own prerequisite checks.

Publication rejects foreign/manual changes and final symlinks, atomically replaces owned files and removes only known prior outputs. A user-manager reload registers definitions. New applications remain stopped. Immediate edits restart only previously running members when runtime settings changed. Enable/disable changes source `[Install]` boot dependencies without restarting members or invoking `systemctl enable` on generated services. Source and active-container fingerprints distinguish registered settings from running settings; deferred changes can report `restart_required`.

`managed_service_start`, `stop`, `restart`, `enable` and `disable` are shared job operations. Start/restart check required file references, registered definitions/dependencies and cgroup v2; stop verifies the resulting unit states. Enable/disable persist authoritative boot policy through the coordinator. User-manager/Podman/generator access remains required; startup configuration alone does not establish lingering or successful boot behavior.

Current limits: the full health/schema and provider restart/recovery matrix remain open. Dependencies currently require other Quadlet applications. Removed definitions require stopped workloads; uncertain removal replay is refused. Network/drop-in conflict coverage, publication crash recovery and broader portability cases remain incomplete. Dedicated Ubuntu guest checks have passed Quadlet lifecycle, boot enable/disable cold cycles and deliberate partial-group Start recovery; there is still no uninterrupted final-build Debian native matrix or full daemon-restart coverage. Command fixtures and installed-generator dry-runs cover additional failure cases.

## Readiness and Applications status

`managed_config_check` refreshes native prerequisites and static filesystem checks; `managed_services` supplies redacted configuration health and selected per-application state. Quadlet prerequisites enumerate missing programs, engine access, cgroup v2, user-manager access and lingering. Both Podman adapters inspect the effective rootless networking command and helper discovery reported by `podman info`; a missing selected pasta/slirp4netns helper blocks startup with a native-package remedy. Rootful engines do not require those rootless transport helpers. Generated application networks require Netavark and Aardvark DNS in both scopes; their native executable discovery is checked in the same metadata response. Missing components block startup with package remedies; an unreported backend remains unknown and an unsupported backend is refused. Unreadable runtime metadata remains an actionable blocker. Native results are cached for ten seconds per configuration, with a separate runtime-check timestamp and explicit refresh. Issues propagate to affected resources and their dependent services. Missing adapters and unavailable checks produce blocked/unknown results rather than a readiness claim. Lingering blocks boot enablement but is separate from current-run startup requirements.

Configuration-wide blockers, including a saved server-settings change awaiting restart, pending/failed apply journals, invalid apply journals (unknown) and unresolved backup recovery, are copied to every affected service/share as well as retained at configuration scope. Application issue lists and startup controls therefore use the same blockers as the mutation guard. Native readiness caches retain native probe results only; accepting new startup settings clears the derived restart issue without waiting for cache expiry. A configured file with no application definitions displays the initial setup guidance; a search with no matches displays a separate empty result.

The shared `managed_config_readiness` operation reads the same file/mount and cached native prerequisites without inspecting running workloads. Missing and malformed configurations have explicit inspectable states. An authenticated global UI alert checks on mount, after management jobs, on tab visibility and every 60 seconds while visible, without activation or installation. It remains mounted across navigation, retains previous issues when a refresh fails, exposes unknown results, links to configuration/applications/host dependency management and lists every issue. Restart/reload derives current health again from configuration and host state; readiness is not another persisted source of truth. Explicit recheck refreshes native probes. A missing manifest is treated as an unconfigured installation, while an unreadable/malformed existing manifest prompts repair. This establishes the alert workflow for implemented checks, not exhaustive host readiness.

Both Podman adapters additionally verify that the account's `dbus.socket` is loaded and active with a bounded read-only user-manager query. A working systemctl private socket does not prove that the session bus required for systemd cgroup delegation exists. Missing/inactive sockets block Podman activation; unreadable/malformed results remain unknown. Docker retains its independent engine/socket requirements. Shared APT session-package selection and explicit bootstrap socket startup address initial setup without restarting the user manager; direct dependency installation may still require that explicit user-socket setup.

The Applications page shows lifecycle controls, observed running state, independent boot policy, configuration revision status and actionable startup issues. Runtime state remains observed when preflight has blockers: a running workload must not disappear into an unknown state merely because a startup prerequisite is now broken. It disables start/restart/enable when the corresponding required checks are blocked. Existing host service/software screens retain direct management. Guided definition/edit forms and a YAML recovery view are available. The global banner distinguishes blocking errors, inconclusive checks and nonblocking warnings; a missing initial image asset does not falsely block a usable existing VM disk. Application inventory now includes sanitized, sorted member states for configured container groups when the adapter obtains an engine inventory; absent members are labeled not running, not assumed deleted. Raw engine labels, command lines and private environment are not returned. The explicit `managed_service_logs` read-only tool serves at most 2,000 requested entries and retains at most 128 KiB of output. Quadlet merges the generated user-unit journal, Podman/Docker Compose reads the exact managed project, and Incus shows ownership-verified VM instance diagnostics (not guest application logs). Logs can contain private application data, are never fetched as part of inventory, and are requested only via Applications or MCP. This initial reader does not claim libvirt guest logs, a portable VM console, complete application health checks, account mapping/SELinux probes, image availability or restore workflows.

## Initial Compose adapters

Docker and Podman share the typed Compose renderer and adapter. Podman explicitly selects the installed `podman-compose` provider for validation, readiness, runtime operations and boot launchers; installing Docker cannot silently switch it to Docker Compose and introduce a Podman API-socket dependency. Generated projects have stable names, explicit native command context and a private owned Compose file beside the manifest. Boot launcher sources also live in that generated-artifact tree, outside the systemd unit search hierarchy; systemctl links them into the user manager. Literal dollars are escaped in inline settings. Bind mounts use long syntax with `create_host_path: false`; missing persistent data is not replaced automatically. Candidate validation uses a private temporary file and the installed provider's `config`, sending both output streams directly to discard. It does not require provider-specific quiet flags or capture resolved configuration; a nonzero result still rejects publication.

Boot uses an owned regular systemd user oneshot unit linked from a private directory. Its explicit enable/disable operations never use `--now`; disabling relinks the definition without boot activation. The unit launches `compose up --detach --no-build` at boot and remains active/exited to retain the cgroup containing detached podman-compose children. It has no restart loop or ExecStop; current-run state and controls still come from the engine. Removal requires stopped containers, then stops/disables only the matching owned launcher before deleting its source. Fragment identity resolves systemd's search-path link to the checked owned source, accepting a legitimate link while rejecting a foreign file even with identical bytes. Unmanaged drop-ins, stale manager definitions and in-progress boot operations block removal. Containers currently have restart policy `no`, and the oneshot has no restart supervision: daemon restart/crash recovery is not provided by this initial policy. This avoids a disabled application starting from a conflicting engine restart policy. Other restart policies require the planned verified provider matrix before being advertised.

Saving a definition publishes native configuration without creating or starting containers. Immediate changes reconcile previously running members only; stopped applications remain stopped. Start creates/starts from the current definition. Restart uses forced recreation so saved configuration is loaded. Same-engine Compose application dependencies start in defined order; cross-backend dependencies remain unsupported. Removal requires stopped containers, verifies owned files before native `down`, omits volume removal, disables boot links and removes known generated outputs. Source and active fingerprints expose deferred changes.

Command fixtures cover both native inventory shapes (Docker newline objects/string labels and Podman arrays/map labels), literal rendering, boot-policy separation, ownership rejection and recreation semantics. Dedicated disposable-guest tests have also exercised both Compose providers' lifecycle/deferred updates and data-preserving removal; Podman service-name DNS/HTTP checks passed. Actual cold boot exposed a launcher lifetime bug and a subsequent Netavark failure of unproven cause. After the launcher/network-ordering changes, a normal-environment Ubuntu guest completed enabled-from-stopped and disabled-after-running cold boot across all five backends. This does not establish the earlier failure's cause, all restart profiles or Debian acceptance. See the [native evidence and limits](../operations/native-acceptance.md).

Runtime observations carry sanitized resource issues to the shared Applications inventory used by web and MCP. A failed owned Compose boot launcher produces a warning independently of definition drift and current container state, including partial startup. The warning uses the existing native status query, remains until the launcher leaves failed state, and does not block explicit Start/Stop recovery. Foreign launcher failures are not attributed to the managed application. Raw native diagnostics and resolved Compose configuration are not included.

Compose and Quadlet share bounded engine inventory parsing and configured-member accounting. A group with some configured containers running reports `partially_running` with an explicit running/expected count and a recovery warning; it is not labeled fully running or treated as definition drift. Start/Stop remain available. Unit/old-member activity without any desired running container reports unknown runtime state, while conservative native activity remains available to apply/removal safety checks. Duplicate native member identities are refused. Each observation is fresh, so runtime warnings clear when the group is complete without waiting for prerequisite-cache expiry. Applications renders these states as readable words.

Both Compose adapters and their boot launchers share one argument builder and run from the generated definition's directory. They use an absolute `--file`, explicit project identity and `/dev/null` environment input, without `--project-directory`, which the packaged Podman Compose provider does not accept. Boot units use a single unquoted WorkingDirectory path with literal percent escaping; ambiguous control/backslash/trailing-whitespace paths fail validation rather than producing an invalid unit.

Podman Compose launchers add Wants/After on the packaged `podman-user-wait-network-online.service`, matching [Quadlet's implicit network ordering](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html#implicit-network-dependencies). A user unit cannot order itself against the system manager's network-online target directly. Shared Podman readiness checks verify that this bridge unit is loadable for both adapters, with a bounded read-only user-manager query. It needs no persistent enablement because the workload dependency starts it; missing/masked units block boot enablement while preserving current-run controls. The native helper has a bounded timeout. This corrects a missing boot prerequisite; it is not proof of the cause of the earlier intermittent Netavark failure.

Docker Compose readiness separately probes the system `docker.socket` load/enable state with a bounded read-only command. Persistent socket enablement is required for boot policy; disabled/runtime-only/missing states are blockers and failed/malformed checks remain unknown. These `autostart` issues propagate to affected services without blocking current-run startup when Docker is accessible. The host installer enables the socket and daemon explicitly. The Ubuntu guest's selected cold-boot cases passed, but Docker daemon restart and broader provider profiles are not yet accepted.

## Initial libvirt VM adapter

The libvirt adapter renders domain XML using typed XML encoding and validates a private temporary candidate with `virt-xml-validate`. Stable UUID/MAC values come from the authoritative configuration. Names are derived from service IDs. Explicit file-backed disks require `format: qcow2` or `format: raw` on their storage definitions. The initial hardware profile is x86_64, BIOS, a q35-compatible machine, host-model CPU, virtio disks/NIC, a VGA device and a serial console. Headless operation still includes VGA because the tested Debian cloud image's BIOS/GRUB boot path fails without it; no graphics listener or remote display is configured. The VGA model is part of persistent/live hardware comparison, while libvirt-derived video addresses/memory/aliases remain native defaults. Optional `architecture`, `machine` and `firmware` fields are explicit; unsupported firmware/architecture settings are rejected rather than ignored.

Libvirt hardware readiness is scoped to the configured connection. After verifying the connection, a bounded `domcapabilities` query requests the supported x86_64/q35 KVM profile. A system daemon can provide KVM through its own QEMU account without giving server-man direct `/dev/kvm` access. A session connection must expose KVM through that account's own daemon. Failed probes block startup; malformed, duplicate, wrong-profile or trailing capability data remains unknown. Native diagnostics are not exposed. This checks profile availability rather than successful guest startup.

Domain metadata uses a private XML namespace with resource/configuration/runtime fingerprints. Reads verify UUID, name and ownership before mutations; registered/live definitions are compared on managed hardware fields while allowing libvirt-generated device addresses and defaults. Libvirt KiB normalization and q35 machine aliases are handled. A network interface's daemon-resolved live bridge is ignored only when the requested network matches; explicit bridge bindings remain compared. Native autostart is checked independently of running state.

Definition and updates call `virsh define --validate` without starting a guest. Immediate incompatible running changes are refused; next-start saves register persistent XML and report a running revision mismatch. Restart waits for graceful shutdown before starting the persistent definition, rather than requesting a guest reboot that would leave pending configuration unused. Stop is bounded to 90 seconds and never falls back to destroy. Undefine requires shut-off state and retains disks, NVRAM and TPM state; ownership and stopped checks precede removal.

Current limits: image provisioning, UEFI/NVRAM configuration, complete host capability/network/backing-chain/account access checks, VM boot-dependency orchestration, richer native-field comparisons, backup state capture and real lifecycle/boot integration are still open. The adapter rejects image-only definitions until an image has been provisioned into declared disk storage. Tests exercise command fixtures and an installed native XML schema validator. A disposable native guest has passed real stopped definition/update, independent boot policy, lifecycle/restart and deferred updates while preserving UUID/MAC and disks on removal. Actual reboot and broader profile/distribution acceptance remain open.

## Initial local Incus VM adapter

The Incus adapter uses fixed `incus --force-local query` argument arrays for bounded read-only JSON with explicit API project selection. Native `init --vm --no-profiles` and `config edit` receive definition JSON on stdin; payloads never enter process arguments. Native start/stop commands use explicit local instance/project scope and wait for completion. Stdout/diagnostics are discarded or sanitized. Creation waits for the stopped virtual machine without starting it. Sources currently require a locally available image alias or fingerprint. Explicit project/pool/network bindings are checked before native publication; definitions use no inherited profiles. Root storage uses `root_size_gib` (20 GiB when omitted), with explicit CPU/memory, MAC, boot autostart and UEFI secure-boot settings. Host bridge NICs and managed networks have separate native representations. VM readiness verifies the native QEMU executable and its modular SPICE option through a bounded help-only probe, without opening KVM or starting a guest. The probe recognizes QEMU's complete SPICE option-help output even when help exits 1; a missing component produces an actionable dependency blocker.

Owned YAML artifacts are derived outputs. Instance user metadata records the authoritative resource identity and fingerprints; Incus owns its native volatile UUID and other runtime keys. PUT updates retain existing volatile keys rather than setting a new native identity. Existing image replacement, shrinking root disks and changing pool/project are rejected. Definition removal for an existing instance is blocked until a separate data-preserving export/retention workflow is implemented: ordinary Incus deletion would remove guest storage. If native inventory proves the instance absent, a reviewed removal can delete only its checked derived definition and verifies continued native absence; failed creation does not trap an empty configuration entry.

Start records the requested runtime revision and waits for a running state; stop/restart uses graceful native stop with a 90-second timeout, no force flag, and verifies completion. Stopped creation/update prepares the runtime marker for the next native boot, so Incus autostart can load the definition without a server-man Start call. Running publication retains the prior loaded marker; a missing/unverifiable prior revision cannot be stamped as the newly loaded runtime. After confirmed graceful stop, a metadata-only update aligns tracking with the native persistent revision, bounded to ten seconds and validated as a digest. It does not apply hardware settings left by a failed desired save. Boot enablement changes do not stop/start the VM.

Immediate changes requiring a different runtime revision are refused while running. Next-start currently attempts native persistent configuration edits, which can fail when a packaged provider cannot apply the corresponding live mutation (observed for a Debian Incus memory increase). That release behavior and complete live/external-operation tracking remain open; the stopped/native-autostart tracking correction does not implement deferred hardware coordination or waive its requirement.

A dedicated Ubuntu guest has verified stopped creation/update, independent boot policy, current lifecycle, deferred update and stable native identity through reviewed continuation after dependency repair. Existing-instance removal, custom-volume/disk mapping, remote image acquisition, complete capability checks and actual boot orchestration remain open. LXD/classic LXC code and tools have been removed. Command fixtures cover additional failures; the native evidence does not establish all profiles or distributions.

## Authoritative Samba/NFS adapters

The central share model now includes publication, storage reference, read-only access, Samba guest/browseability/users and NFS client/root-squash/security fields. NFS defaults to root squashing and `sys`. Adapters derive a complete published protocol set from central YAML; disabled definitions remain in YAML and are omitted from native output. Paths are resolved against the manifest and normalized through the existing native share validator.

The existing share implementation supplies one shared transaction for both direct host operations and authoritative set replacement. Previous generated metadata is observed integrity/rollback information, never desired input for central reconciliation. The complete desired protocol set replaces stale owned entries while preserving unmanaged configuration/data. Candidate validation, stale revisions, targeted NFS operations, Samba shadow validation and bounded file/runtime recovery remain in this common implementation.

When privilege routing is enabled, helper-only `shares_definitions_inspect`, `shares_definitions_validate` and `shares_definitions_apply` operations receive typed JSON definitions through stdin. The helper independently validates fields and fixes native output paths; these low-level endpoints are not registered on application transports. Native candidate validation runs before the central configuration commit. Protocol-wide prerequisite validation is batched and cached, while Samba missing local identities receive resource-scoped diagnostics.

`managed_shares` returns authoritative publication/configuration status; `managed_share_publish` changes the central toggle and applies the protocol set without altering directory data or host daemon enablement. Publication checks do not prove client usability or revoke existing Samba sessions. Unused missing storage remains in configuration health but no longer blocks unrelated apply or unpublication.

File shares uses central definition forms; old direct native share-edit tools and their unused UI have been removed. Native metadata comments remain integrity markers in derived fragments. Disposable-guest SMB3 and NFSv4.2 clients have verified reads/writes, read-only denial, authentication/user/client restrictions, root squashing, policy changes and fresh-session denial after unpublication; see the [native evidence and limits](../operations/native-acceptance.md#sambanfs-client-acceptance). Complete drift repair, daemon/account/credential/ACL diagnostics and portable restore remain open. Ordinary tests use temporary files/native-command fixtures; live client acceptance used isolated namespaces only inside the dedicated guest. No workstation exports or shares were changed.

## Typed definition editing and recovery UI

`managed_config_model` provides private typed form data under the existing write-enabled editor policy. `managed_resource_plan` and `managed_resource_save` accept service/storage/share/binding/private-file-reference edits with the current central revision. They reject unknown typed fields, validate the complete resulting configuration (including dangling references), and use the same coordinator preview/save workflow as YAML. Removing a reference does not delete its underlying data. Malformed YAML must be repaired through the recovery editor before typed forms can operate.

Applications now has container-group and VM create/edit forms, explicit backend selection (Docker Compose only; Podman defaults Quadlet), resource settings, existing storage mounts/disks and host-binding selectors. Existing backend/kind/IDs are fixed; supported edits preserve other typed settings and VM identities. Review shows affected resources before acknowledged save, with immediate versus next-start publication. Defining a service leaves it stopped, independently of boot enablement.

Configuration manages storage references, network/pool/project bindings and private-file references. Its YAML view supports advanced editing and malformed-config repair, revision conflicts and inspection/retry of incomplete apply. File shares now uses the same editor and authoritative publication operations; native package/daemon setup remains a separate explicit host action. Secret file contents are never loaded into form data; inline non-secret environment remains private configuration data.

These forms cover the current supported schema rather than every target feature in the plan. Provisioning new disk data, full diagnostics/logs, container health/readiness semantics, richer VM hardware settings, full interruption recovery, backup/restore are still open. Browser fixtures check request payloads and real write-disabled rejection; they do not establish successful native mutation.

## Host-service controls for generated units

Ordinary host system/user units remain direct systemd operations. For owned application user units, Services details identify the application; start/stop/restart route through its coordinator, and enable/disable persist central startup policy. Direct reload is refused in favor of applying the definition. Routing is installed before the privileged wrapper, keeping managed user actions under the workload account. Generated user units reserve the `sm-` prefix: missing, unknown or stale matching user units cannot be directly mutated through Host services even when the manifest is otherwise valid. A broken manifest also blocks these reserved writes until repaired. Ordinary system units and unrelated user units retain direct controls.

## Configuration history and reviewed revert

Configuration exposes up to eight private previous revisions through `managed_config_history` and `managed_config_history_read`. Reads use content hashes, directory/file type and permission checks, bounded directory enumeration and the same descriptor-based private-file reader as current YAML. Malformed historical YAML can be inspected or copied into the recovery editor; it cannot be selected for direct revert. Referenced private files are never opened. History operations follow the write-enabled private editor policy on both transports.

`managed_config_revert_plan` previews a selected revision against the current revision. `managed_config_revert` is an acknowledged job using the normal validation, identity, journal, publication and verification path; next-start is the UI default. Revision identifiers are content hashes, so restoring identical bytes may reuse an earlier hash. Revert restores desired definitions rather than data or client effects, never starts stopped workloads, and can fail on missing prerequisites, ownership conflicts or unsupported native changes. Stale revisions are refused. Invalid current YAML remains repairable, but partially decoded invalid definitions never authorize native removals or identity changes.

An explicit revert can supersede a failed/saved/blocked/applying transition after checking its unresolved removals. A removed resource must be restored by the selected configuration or proven absent; otherwise revert refuses to discard its recovery tracking. Prepared transitions require inspection/retry first. During the new prepared stage the journal retains one bounded copy of the superseded transition. If the new YAML was not committed, retry restores that prior journal; after commitment retry reconciles the newly selected desired definition. The superseded copy is discarded after durable save. Native effects remain best-effort reconciliation, not a global rollback transaction. Complete interruption/fault coverage and live-backend recovery verification remain open.

## Explicit new-data provisioning

`managed_storage_plan` and acknowledged `managed_storage_create` jobs create new empty directories or blank sparse raw/qcow2 disks for existing storage references. Configuration offers a separate review form, including an explicit new-data acknowledgement. Missing data is never created by save, preflight, Start or restoration. Existing paths, external storage, symlink parents, private-file/configuration collisions, unowned/group-writable parents and missing expected mounts are refused. Parents must already exist; creation uses private defaults under the application account, including inherited setgid group ownership. No chown or privilege escalation is attempted.

Plans capture the configuration revision, parent identity, owner, destination, capacity and affected consumers. Creation rechecks the plan and consumer state before publication; services must be verified stopped and shares unpublished. Directories use 0700 and disk files 0600. Raw files are sparse; qcow2 creation uses fixed native qemu-img arguments against a held newly created staging descriptor, followed by native format/size/backing verification. A no-replace hard link publishes the disk after sync. Native failures remove temporary output rather than expose a partial destination. Parent-sync failure after publication is reported as uncertain completion, not silently retried.

Disk capacity is bounded to 1–4096 GiB and not reserved; initial free-space checks do not guarantee future allocation. Blank disks contain no guest OS. Image acquisition, guest installation, external/backend-volume provisioning, nested parent creation, account/ACL/SELinux setup and live guest acceptance remain separate unfinished work. See [QEMU image utility](https://www.qemu.org/docs/master/tools/qemu-img.html) for native create/info semantics.

## Initial VM image assets

Owned file storage can declare an optional creation-only `source` with a relative `assets/` path, explicit raw/qcow2 format and pinned SHA-256. The storage editor and provisioning review use the same model. Sources cannot overlap managed data or private-file references. Provisioning checks real directory parents, independent regular files owned by the account/root, permissions and source metadata; review tokens include source identity/size/mtime. The job verifies the full checksum before and after native conversion and checks the resulting disk's format/virtual capacity before no-replace publication. Sources remain unchanged. Native tools use held source/destination descriptors; image bytes and diagnostics are not copied into job output.

A bounded qcow2 header rejection gate runs before native inspection to refuse backing files, encryption and incompatible features (including external data files and dirty/corrupt flags); QEMU remains the image validator. Both raw/qcow2 directions use explicit native formats and an already initialized destination. Larger virtual capacity does not resize a guest partition/filesystem. Downloading images, initialization credentials/cloud-init and boot/guest integration remain separate work. Libvirt image definitions use these storage sources; the VM's `image` field remains an Incus image identifier and is refused by the libvirt renderer.

Initial sources affect desired configuration fingerprints but are excluded from runtime fingerprints. Editing source metadata never reclones an existing disk, and save/start never invokes provisioning. A missing initial asset is reported as a warning when a disk already exists; missing disk data stays blocking. Preview checks metadata/native format; full checksum verification occurs only inside the acknowledged creation job. Incomplete staging cleanup is reported explicitly. See the upstream [QEMU image utility](https://www.qemu.org/docs/master/tools/qemu-img.html) and [qcow2 header format](https://www.qemu.org/docs/master/interop/qcow2.html).

## Portable backup input inventory

`managed_backup_inventory` and Configuration's **Review backup inventory** inspect the selected current revision and bounded native guest dependencies without copying data, reading private-file contents or changing workloads. Private inventory follows the write-enabled editor access policy on HTTP/MCP. [Backup design](backup.md) describes its input/requirement contract and current limits. Service data references are shared across backup/provisioning, startup blockers and resource fingerprints, rather than copied into each workflow.


Interrupted backup capture has a separate private journal sharing apply-journal I/O. Pending recovery blocks conflicting managed operations and surfaces in global configuration health. Configuration and MCP provide reviewed resume or release without replaying capture or changing boot policy. See [backup recovery](backup.md#interrupted-workload-recovery) for state transitions and limits.

Compose launcher lifetime follows [systemd oneshot/RemainAfterExit semantics](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html): allowing a oneshot to become inactive can terminate detached child processes still in its cgroup. A temporary native fixture confirmed that keeping the unit active/exited preserves the same container after launcher completion.
